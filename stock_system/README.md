## 五、三个必须知道的数据口径问题

### 1. 复权用前复权序列，不用后复权

东财返回的 hfq 序列不是"原始价 × 固定因子"，其单位因子逐日漂移，日涨跌幅与原始价对不上（实测 0.87% vs 0.66%），长周期累积失真。qfq 序列满足 `qfq_t = raw_t × (F_t / F_T)`，等价于归一化到最新日的后复权序列，日收益率与真实收益一致。

验证：000034 于 2026-05-19 实施 10 转 4 派 0.73，原始价从 41.57 跌到 30.96（显示 -25.52%），复权后实际涨幅 **+4.45%**，与除权参考价 29.64 的计算结果一致。

**限制**：qfq 会随新的除权整体平移，除权后需对该股全历史重算（M2 实现除权检测）。

### 2. 除权日的原始涨跌幅不可用

`fact_daily_quote.pct_chg` 是东财返回的原始价涨跌幅，除权日会显示成暴跌（如 -25.52%），不是真实亏损。因此表里另存 `pct_chg_adj`（复权涨跌幅，除权日亦正确）。

**筛选引擎的单日涨幅条件必须用 `pct_chg_adj`，不能用 `pct_chg`。**

### 3. 财务数据全部是推定公告日

akshare 财务摘要只返回报告期、不返回公告日，因此按法定披露截止日推定：  
一季报 4/30、半年报 8/31、三季报 10/31、年报次年 4/30。全部标 `ann_date_source='estimated'`。

`as-of` 切片因此是保守的（永远不早于真实公告日），不会产生前视偏差，但会略微滞后。


条件树支持 AND/OR 任意嵌套，运算符 11 类：
`gt/gte/lt/lte/eq/neq`、`between/not_between`、`in/not_in`、`is_true/is_false`、`pct_between`、`top_n`。

### 4. M2 期间修正的两个数据错误

**PE(TTM) 不能用最近四期直接相加。** 财务数据是累计值（Q1、H1、Q3、年报），四期相加会把一季度算四遍。正确公式：

```
最新为年报 → TTM = 年报值
否则       → TTM = 上年年报 + 本期累计 − 上年同期累计
```

实测国药一致：错误算法得 PE 3.8，修正后 10.1（市值 114 亿 / TTM 净利 11.3 亿），与市场一致。

**股本来源要分市场。** 深交所列表接口自带股本（且是带千分位逗号的字符串，需清洗）；沪市与北交所没有，只能用快照的「总市值 ÷ 最新价」反推。反推值会在增发、送转后滞后，因此只补空值，不覆盖交易所给出的准确值。

### 每日数据更新（10-11-03 新增）

调度器里固定注册一个 `daily-data` 任务，**每天 16:00**（Asia/Shanghai）依次执行：

```
行情增量 → 财务增量（skip_existing）→ 指标重算 → 横截面缓存失效
```

三个采集函数各自写 `sys_task_log`，所以数据页的「采集任务」能看到分段进度。

设计要点：

- **非交易日直接跳过**：交易日历表只收录交易日，查不到即跳过。否则周末会为 5570 只股票各发一次请求，空跑约一小时
- **时间写在 `api/main.py` 顶部**：`DAILY_UPDATE_HOUR` / `DAILY_UPDATE_MINUTE`
- **必须注册在 `load_jobs()` 内**，不能只在启动时加一次——`load_jobs()` 开头有 `remove_all_jobs()`，否则每次重建策略定时都会把它清掉
- **放在策略定时之前**（16:00 vs 18:30），保证策略跑的是当天数据。如果顺序反了，策略会静默使用前一交易日的行情

数据页新增「定时任务」区块，展示每个 job 的中文名、执行规则与下次运行时间（`GET /api/v1/scheduler` 返回 `label` / `cron_human` 字段）。

### 界面触发采集

数据管理页「数据维护」区域提供六个操作，全部异步执行：

| 按钮 | 任务 | 说明 |
|---|---|---|
| 同步 | `stock_list` | 沪深北全市场代码、名称、上市日期、股本 |
| 补齐 | `shares` | 沪市与北交所无股本，用快照市值反推 |
| 增量同步 | `quote`（不传 start） | 从库中最大交易日次日开始 |
| 补齐历史 | `quote`（start=界面上选的日期） | 起始日可选，默认 2024-01-01 |
| 同步 | `financial` | 全市场财报，约 100 分钟 |
| 重算 | `indicator` | 行情变动后重算全部标的 |

机制：

- `POST /api/v1/tasks/run` 起线程执行，立即返回；`GET /api/v1/tasks/status` 查运行中任务
- 同名任务互斥，重复点击返回 409
- 前端每 4 秒轮询，任务结束后自动刷新统计卡片与任务日志
- 服务重启会中断进行中的任务（采集器有断点续传，重跑即可）

**任务链**：`financial` 成功后自动接续 `indicator`。理由很直接——财报补齐后如果不重算指标，PE/ROE 仍然是空的，筛选照样跑不出结果。失败的任务不接续，避免在脏数据上继续算。

触发接口的返回体带 `next` 字段，告知会接续哪个任务。

**补历史的起始日**：按钮左侧的日期框可选（**默认 1990-01-01**，上限为今天），选完点「补齐历史」即按该日期发起。

同一默认值在 `config.py` 的 `HISTORY_START`（`STOCK_HISTORY_START` 环境变量可覆盖），用于命令行不带 `--start` 且库中无数据的场景。两处保持一致，都是 1990-01-01。

实测起始日对接口是生效的（akshare 原样传给东财）：

| start_date | 000001 返回 |
|---|---|
| 20240101 | 685 行，起于 2024-01-02 |
| 19900101 | 8509 行，起于 1991-04-03（该股上市日） |

**1990 年起的实测影响**：库内现有 2010-01-04 起 1099 万行；补到 1990 年需再增加约 **358 万行/表**（按各年已上市数 × 交易日估算），日线表 +476MB、三张事实表合计约 **+1.4GB**。

分区无需调整：事实表首个分区是 `p2005`（上界 `TO_DAYS('2006-01-01')`），RANGE 分区会覆盖低于该上界的全部日期，1990—2004 的数据落在 p2005 内，实测可正常插入。代价是 p2005 会比较大（约 360 万行），但筛选都是按单日查询、裁剪到具体分区，不影响日常使用。

注意耗时**不是**由跨度决定的——采集器对每只股票只发一次请求，取回整段区间，所以 5570 只的成本基本固定（约 50—90 分钟）；跨度大只是单次响应的数据量变大，略慢一点。想让耗时明显下降，只能缩小股票范围（`--limit`）。

### 执行对比

结果栏「执行对比」按钮，选两次执行记录后展示三组：

- **共同命中**：两期都在，策略稳定筛出的标的
- **仅 A 命中**：A 有 B 没有，说明条件收紧后消失
- **仅 B 命中**：B 新增的标的

`GET /api/v1/screen/runs/diff?a=&b=`，按 `fact_screen_result` 的代码集合做差集，比 `hit_cnt` 更准（后者是分页后的数量）。

### 断点续传

财务采集支持跳过已有财报的标的（`skip_existing=True`）。服务重启后重跑只补缺口，不必从头开始——实测 5577 只中已有 1772 只，任务总量自动降为 3805。

需要更新已有财报（新报告期发布）时，用「全量刷新」入口强制重采。

### 已知限制

- 财务覆盖仍在补齐中（采集器按 `skip_existing` 续跑），未覆盖的标的 PE/ROE 显示"—"
- 筛选结果最多载入 1000 条（超出时工具栏会提示真实命中数）

### 策略编辑

策略列表每行有「编辑」：点后把该策略的条件载回工作台，顶部出现蓝色编辑条——显示策略名、版本号、当前条件条数，右侧是「保存修改 / 另存为 / 退出编辑」。

保存走 `PUT /api/v1/strategies/{id}`，`version` 自增；「另存为」走 `POST` 建新策略，并自动切到副本继续编辑（避免改完副本又误覆盖原策略）。切换模板或点「退出编辑」会离开编辑态，未保存修改有二次确认。

**为什么不做一个独立的策略编辑器**：工作台里的条件卡片已经支持改阈值、删除、从指标库添加。另做编辑器等于把同一套交互实现两遍，而且两处容易长出不一致的能力。

**边界**：工作台只支持平铺 AND 条件组。载入时接口返回 `nested` 标记（条件树里是否还有子 `children`），为 true 时前端直接拦下并说明原因，不会静默丢掉嵌套结构——静默丢弃会导致保存后条件被悄悄改写，这种问题很难发现。

接口侧同步改了两处：`GET /strategies/{id}` 把 MySQL 返回的 JSON 字符串解析成对象并附带 `cond_cnt`/`nested`；`PUT` 补了名称非空校验与重名 409（原先是 IntegrityError 直接 500）。

### 列表页对齐与样式作用域

`.grid-table`（策略/自选/数据三个列表页）与工作台结果表（`.table-wrap`）共用 `th`/`td`。早期样式里 `table`、`thead th`、`tbody td` 是**裸元素选择器**，没有限定作用域，会溢出到 `.grid-table`：

- `tbody td{text-align:right}` → 列表页单元格被右对齐，而表头因 `.grid-table th` 优先级更高仍是左对齐，于是整列错位
- `table{min-width:1120px}` → 列表页表格被强行撑到 1120px，窄窗口下横向溢出

现在四段规则全部限定在 `.table-wrap` 下。改动这类公共样式时，务必确认没有新增裸 `td`/`th` 选择器。

对齐规范：

| 列类型 | 规则 | 适用 |
|---|---|---|
| 数值 | `class="num"` 右对齐 + `tabular-nums` | 收盘、涨跌幅、换手率、条件数、执行次数、进度、成功/失败 |
| 时间/代码 | `class="mono"` 左对齐 + 等宽数字 | 加入时间、最近执行、更新时间、开始、结束、股票代码 |
| 操作 | `class="act"` 右对齐 + `nowrap` | 详情/移除、编辑/执行/定时/删除 |

右对齐列在末尾按钮上要注意 `.mini-btn` 自带 `margin-right:6px`，会顶开 6px，需 `:last-child{margin-right:0}`。

chip（`.tag` / `.badge`）默认带 1px 6~7px 内边距，盒子对齐表头但**盒内文字会比表头缩进 6px**。列表页首个 chip 用 `margin-left:-6px` 抵消，让文字左缘严格重合。

### 浏览器缓存

`index.html` 由中间件统一加 `Cache-Control: no-cache, must-revalidate`，浏览器每次回源校验（带 ETag，未变更返回 304）。

> 注意：给 `@app.get("/")` 的 `FileResponse` 单独加 header 是无效的——`app.mount("/", StaticFiles(html=True))` 在路由之后仍会接管 HTML。必须用 `@app.middleware("http")` 按 `content-type` 判断。

前端改完看不到效果时，先确认响应头有没有 `Cache-Control`，再怀疑代码。

> 验证方式：Edge 无头截图 + Pillow 逐列测量像素坐标。表头与数据块的左/右边缘误差应 ≤2px（CJK 字形有 1—2px 侧边距）。

支持 `#watch`（自选股）、`#strategy`（策略管理）、`#data`（数据管理）直接打开对应页，可加书签。切换页面时同步更新地址栏 hash，工作台对应无 hash。

### 结果表的排序与分页

14 列表头全部可点击排序：数字列默认降序、文本列默认升序，再点一次反向。空值恒排末尾，不受升降序影响。

分页在表格底部，每页 20/50/100/200 可选。筛选请求固定取 1000 条，命中超过 1000 时工具栏出现橙色提示「命中 N 条，仅载入前 1000 条」——**命中数是截断前的真实总数**（后端 `run_screen` 在 `head(limit)` 之前先取 `len(hits)`）。

> 这个细节踩过坑：最初 `hit` 直接取 `len(items)`，结果 limit=1000 时永远显示「命中 1000」，看起来像全市场只有 1000 只符合条件。

### 执行对比钻取

对比弹窗里点任一标的，会关闭弹窗、切回工作台并加载该股详情（K 线、财务趋势、技术指标）。

- 若该股在当前结果集中，直接复用结果行，评分与命中溯源都在
- 若不在（比如「仅 A 命中」的标的），走独立详情模式：头部行情从详情接口补齐，评分隐藏，命中溯源位置显示说明文字而非空白

### 筛选性能

横截面构建（技术指标 + 行情 + as-of 财务）是全市场筛选的主要成本，且随股票数与财务表行数增长。两处优化：

1. **合并财务查询**：原先是两条 SQL 各做一遍 `ROW_NUMBER()` 窗口（取最新一期 / 取最近 8 期算 TTM），现合并为一次扫描取 8 期，Python 侧再用 merge 拆出最新一期。
2. **TTM 向量化**：原按股票逐只循环（`.groupby` + `iterrows`），改为整表 merge 计算。
3. **横截面短期缓存**：按交易日缓存 180 秒、最多 3 个日期；任务结束时自动 `invalidate()`，避免读到采集前的旧快照。

实测（5564 只、5221 命中、返回 1000 条）：

| 场景 | 优化前 | 优化后 |
|---|---|---|
| 首次筛选（缓存未命中） | 4.9 s | 2.0 s |
| 连续筛选（缓存命中） | 4.9 s | 0.23 s |
